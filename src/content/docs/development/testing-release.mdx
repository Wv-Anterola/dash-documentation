## Test layers

| Layer | Best for |
| :--- | :--- |
| Unit | Casts, transforms, parsers, scoring, pure layout calculations |
| Component/Storybook | Shared controls and isolated renderer states |
| Integration | Document factories, serialization, collection dispatch, tool execution |
| End to end | Real user workflows across UI, persistence, and undo |
| Manual exploratory | Spatial interaction, media, accessibility, desktop packaging |

Use the lowest layer that proves the contract, then add an end-to-end path for
user-visible integrations.

## Before testing

Record the exact Dash-Web commit, operating system, browser or Electron build,
backend configuration, and any optional providers. Use a disposable account or
workspace for destructive agent and migration tests. A result without its
environment is difficult to reproduce.

For a branch feature, separate three questions:

1. Does the branch implementation work?
2. Does it still work after rebasing or merging the current target?
3. Is there a discoverable entry point in the resulting product?

A clean branch demo proves only the first.

## Document-type matrix

- Create
- Empty state
- Edit
- Link/anchor
- Embed twice
- Undo/redo
- Save/reload
- Permission boundary
- Import/export when relevant
- Loading and external-service failure

Also verify that a new type is declared, constructed, rendered, serialized, and
offered by the intended creation surface. Missing any one of those steps can
leave a valid enum value that users cannot create or a factory result that
cannot render after reload.

## Collection-view matrix

- Empty, one, typical, and large child sets
- Heterogeneous child types
- Add/move/remove
- Selection and drag
- Perspective switch
- Save/reload
- Filter/sort
- Performance/convergence

Switch away from the new view and back again. Then open the same collection in
a second context. View work often appears correct in its first mounted instance
while failing to persist its layout fields or leaking state between contexts.

## Agent-tool matrix

- Schema validation
- Empty and bounded scope
- Access filtering
- Observation content
- Write batching
- Undo/redo
- External failure
- Adversarial source content

For every write tool, capture the proposed arguments, the bounded target set,
the resulting batch, and the undo result. Test partial external failures; a
tool must not leave half a collection changed merely because its final service
call failed.

## Scripting-runtime matrix

- All 151 exact static global names, 12 capability families, 16 decorator
  registrations, and both saved-function dynamic registration sites; use the
  [generated catalogue](/guides/features/scripting/#complete-integrated-global-catalogue)
  as the inventory
- Compile, Apply, Save, Create Function, Edit, Run, and event-only Finish state
  transitions
- `Doc`, string, integer, boolean, and literal-union parameter controls
- Filtered and retained TypeScript diagnostics plus JavaScript function-construction failure
- Ordinary arguments, explicit `undefined`, captures, and `this` precedence
- Primitive capture cache reuse and reference-capture cache exclusion
- Capture persistence for booleans, numbers, strings, document IDs, colon-bearing
  strings, missing documents, and asynchronous hydration
- `{success,result}` and `{success,error,result}` outcomes, including promises
  that reject after synchronous invocation returns
- Computed prior result, explicit cache, array-to-`List` conversion, setter script,
  and advisory `_readOnly_` behavior
- Saved-function startup load, replacement, deletion, case sensitivity, invalid
  identifiers, and already compiled dependents
- Custom-global swap/reset on success and on exceptions
- Permissions, external services, and one named undo boundary for every mutating global

## Server and persistence matrix

- New account and returning account
- Guest and authenticated session
- Socket identity that disagrees with the HTTP session
- Unauthenticated and lower-privilege reads by known document ID
- Unauthorized create, update, single delete, batch delete, and administrative event
- Concurrent edits from two clients
- Same-document ordering and cross-document partial visibility
- Concurrent list append/removal with matching and mismatching expected lengths
- Reconnect after an interrupted write
- Origin acknowledgement, typed database rejection, and optimistic rollback
- Save/reload of newly introduced fields
- All 21 code-registered field `__type` values through serialize, hydrate, nested mutate, and reload; use the [generated wire-type catalogue](/architecture/field-runtime/#complete-serialized-field-catalogue) as the matrix
- Missing and unknown type tags, missing references, and failed script recompilation
- Old stored documents with missing new fields
- Permission inheritance and direct overrides
- Large payload and upload limits
- Iframe source/origin checks and malformed `postMessage` payloads
- WebSocket certificate verification in the deployed TLS topology
- Destructive protocol events absent or server-authorized
- Expected errors without secrets in logs or responses

Use the [synchronization protocol](/reference/synchronization-protocol/) as the
wire-level oracle and the
[security enforcement matrix](/architecture/server-storage-security/#observed-enforcement-matrix)
as the negative-test inventory. Use the
[HTTP and service interface reference](/reference/http-service-interface/) as
the route matrix: cover every affected method/path, request shape, response
branch, direct-versus-supervised registration, and side effect.

## Desktop and optional-service matrix

- Clean install on every advertised platform
- First run without the optional service
- Configured remote provider
- Local Ollama service unavailable, starting, and ready
- Model missing or changed
- Offline launch where supported
- Upgrade over the previous build
- Uninstall or rollback without deleting user data unexpectedly

Do not say that a dependency is bundled merely because the client knows how to
call it. Inspect the package and test on a machine that did not already have
the dependency installed.

## Documentation matrix

Run:

```bash
npm run coverage
npm run quality
npm run check
npm run build
npm run links
```

Review generated pages at desktop and narrow widths. Placeholders are valid
during drafting only when they include an exact capture brief, filename, ratio,
and required alt text.

Also review:

- every new internal link and redirected legacy route;
- navigation order and page titles;
- code paths and commit hashes against the named snapshot;
- screenshots for current UI, legible text, synthetic or non-sensitive data,
  and useful alt text;
- status labels against merge ancestry and a reachable product entry point;
- hard-coded counts against their registries.

## Release gate

A release candidate is ready when the required automated checks pass, the
relevant manual matrices have named evidence, migration and rollback are known,
and the documentation describes both the workflow and its limits. “Works on my
branch” and “the build completed” are useful facts, not release decisions.

Block the release for data loss, permission bypass, unrecoverable writes,
broken persistence, secrets in output, or an advertised path that cannot be
reached. Record lower-severity limitations explicitly rather than relying on
team memory.

## Release record

For each release or deploy, record:

- Dash-Web commit
- Documentation commit
- Build environment
- External provider/model assumptions
- Schema or stored-document changes
- Added, changed, deprecated, and removed capabilities
- Known limitations
- Migration or rollback steps

Documentation should be updated in the feature pull request. A later project
summary cannot substitute for the operating and technical documentation needed
at integration time.

After deployment, test the production URL rather than assuming the hosting
build matches the local artifact. Check the landing page, navigation, search,
one page from each major section, redirects from the old site, and the exact
new route. Preserve the deployment identifier with the release record.
