Technical claims in this site are derived from a reproducible current-source
snapshot and the evidence model below. The revision identifier is maintenance
metadata; normal guides describe product behavior without exposing Git details
in the reading flow.

## Evidence model

Different kinds of documentation require different evidence:

| Documentation claim | Required evidence |
| :--- | :--- |
| A control or workflow exists | Runtime capture or an executable test, plus its reachable interface entry point |
| A document or collection type exists | Typed registry entry and renderer registration |
| A public extension contract exists | Exported symbol, signature, lifecycle behavior, and source documentation |
| A project is integrated | Its implementation is reachable through the current product registries or runtime paths |
| A project was implemented | Surviving source, test, demo, or research artifact identifies the implementation |
| A historical claim is reproducible | Stable publication, artifact, or immutable source link |

The [generated API and registry reference](/technical/api/) extracts document
and collection types, render registrations, agent tools, scripting globals,
routes, environment variables, keybindings, workers, Electron boundaries, and
component-library exports.

## Coverage

The canonical source inventory classifies all tracked files before extracting
symbols. TypeScript and JavaScript are parsed with the TypeScript compiler,
Python with Python's AST, and structured configuration with its corresponding
parser. Unsupported formats and parser failures are reported rather than
silently omitted.

Source-generated reference pages include declarations, signatures, visibility,
documentation, imports, selected registry relationships, and syntax-resolved
calls. Syntax resolution describes static code relationships; it does not prove
that a path executes at runtime. Runtime tests and interface captures remain the
stronger evidence for user-facing behavior.

The complete historical symbol ledger is retained as a
[compressed reproducibility artifact](/assets/data/historical-symbols.json.gz).
The published site reads its compact summary, while the archive preserves every
indexed current and removed symbol without adding hundreds of megabytes to each
page build.

The [implementation archive](/reference/branch-audit/) separately records code
that survives outside the current product. It is research provenance, not the
primary source for current feature documentation.

## Presentation rules

- Guides explain goals, controls, state changes, recovery, and expected results.
- Architecture pages name the models, views, services, data flow, and lifecycle
  contracts that implement those behaviors.
- API pages expose source-derived signatures and link to immutable source
  locations without displaying revision hashes as product content.
- Research records separate question, method, contribution, evaluation,
  limitations, integration status, and provenance.
- Branch names, revision identifiers, and audit digests appear only in
  collapsible reproducibility records or the implementation archive.

## Updating the source reference

1. Fetch the intended Dash-Web source.
2. Record the exact source revision in the reproducibility metadata.
3. Run `npm run audit:branches && npm run audit:source && npm run audit:http && npm run audit:typedoc`.
4. Inspect generated registry and parser-failure checks.
5. Inspect added and removed user entry points.
6. Update capability availability and source paths.
7. Update project statuses only with direct evidence.
8. Run documentation coverage, type, build, and link checks.
9. Record the documentation change in release history.
