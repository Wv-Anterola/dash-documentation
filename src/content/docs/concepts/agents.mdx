## The idea

Dash has two separate model-backed surfaces, and conflating them causes most of
the confusion about what Dash's AI actually does.

The **chatbot** answers. Documents are chunked into a vector store, retrieved
chunks enter the model's context, and answers come back with citations that
resolve to a source document and navigate there.

The **agent** acts. It runs a ReAct loop, calling tools from a registry and
feeding each result back into the message stream. Several of those tools write
to the workspace.

## Why it matters

The second one is a different kind of thing, and Dash is an unusually sharp
case of it.

A chat assistant that gets something wrong produces a wrong paragraph, and you
notice or you do not. An agent that gets something wrong has already
re-tagged forty of your documents. The workspace is persistent and shared, so
the mistake is durable and other people see it.

This is also what makes Dash a good instrument for studying the problem, and
the 2026 cohort used it that way. Retrieved document content and tool results
enter the model's context as messages, which means untrusted content a user
never wrote can carry instructions the model treats as its own. That is indirect
prompt injection, and Dash has the property most test harnesses lack: the
actions land somewhere real and can be reviewed afterwards.

## How Dash represents it

`chatbot/agentsystem/Agent.ts` constructs the registry. A tool is a class with a
schema and an execute method. Twenty-two are registered at startup, and
`tools/dynamic/` exists because the agent can write a new tool and have it
compiled into the running application.

### Inside the Agent class

The registry is a plain record, typed by each tool's parameter list:

```ts
private tools: Record<string, BaseTool<ReadonlyArray<Parameter>>>;
private dynamicToolRegistry: Map<string, BaseTool<ReadonlyArray<Parameter>>>;
```

Every tool extends `BaseTool` (`chatbot/tools/BaseTool.ts`), and the generic
parameter is what lets the same class supply both the JSON schema sent to the
model and the argument types checked at compile time. A tool that declares a
parameter it does not handle will not build.

Two registries rather than one, because tools written at runtime cannot be in
the constructor. `dynamicToolRegistry` holds those, and the deferred webpack
rebuild is what gets them into the running bundle.

The agent keeps two message arrays. `messages` is the conversation;
`interMessages` is the intermediate reasoning stream, appended to as the loop
runs. `thoughtNumber` and `actionNumber` count the steps of that loop, which is
the ReAct pattern made literal: think, act, observe the tool result, repeat.
`StreamedAnswerParser` turns the model's partial output into something the
interface can render before the response is finished.

`AgentDocumentManager` is the boundary between the agent and the workspace, and
`Vectorstore` holds the chunked document embeddings the retrieval side reads.

This is also where the trust problem lives. Retrieved chunks and tool results
both enter `interMessages` as ordinary messages, so a document Dash retrieved
and an instruction the user gave are, by the time the model sees them, the same
kind of thing.

The tools worth separating out are the ones that mutate rather than read:

- `FilterDocsTool` hides documents by applying a filter tag
- `SortDocsTool` reorders them
- `TagDocsTool` re-categorises them
- `CreateLinksTool` adds links

Everything the agent writes goes through `UndoManager.RunInBatch`, so each
action is a named batch that reverts as a unit. That is what makes review
possible at all: without it, undoing one agent action would mean unpicking it
by hand.

Model calls go through `services/openaiService.ts` or, in the desktop build,
`services/ollamaService.ts` against a local model.

## Current limitations

There is no permission model. A tool that can write can write to anything the
user can, and the agent decides when to call it.

Provenance is not captured by default. The 2026 study added a record that
attaches the causing source to each action as it passes through the undo batch,
but it is behind a flag and exists for the experiment rather than as a feature.

Whether a person reviewing agent edits actually catches a bad one is, as far as
we can tell, unmeasured. That is the gap the study was written to address, and
it has not been run yet.
