## The idea

Everything in Dash is a document. A PDF is a document. A collection holding
forty PDFs is a document. The link between two of them is a document, and so is
a chat message, a presentation trail, and an agent.

They differ by their `type` and by which fields they carry, not by being
different kinds of object in the code.

## Why it matters

Most of what Dash can do is a consequence of this one decision.

Consider linking. If a link were a row in a table mapping one document id to
another, then giving it a label would mean adding a column, annotating it would
be impossible, and putting a link inside a collection would be meaningless.
Because a link is a document, all three come for free, and none of them needed
special-casing.

The same argument applies each time someone adds a type. When the 2026 cohort
added policy-checker documents, they did not have to teach the layout system,
the linking system, or the sharing system about policy checkers. Those systems
operate on documents.

## How Dash represents it

`client/documents/DocumentTypes.ts` declares the `DocumentType` enum, currently
fifty-one entries. `client/documents/Documents.ts` holds a factory per type,
and each factory calls `InstanceFromProto` with a prototype fetched by
`Prototypes.get(DocumentType.SOMETHING)`.

Documents inherit from prototypes. A specific PDF is an instance whose prototype
carries the defaults shared by all PDFs, so changing a default on the prototype
changes it everywhere it has not been overridden.

Fields are typed but not fixed. A document can carry arbitrary keys, which is
what makes tagging, filtering, and the schema view work across types that were
never designed to have anything in common.

:::note
`InstanceFromProto` and `Prototypes.get` were written in 2019 and are still
how every document type is constructed. Adding a type in 2026 means the same
four steps it meant then: an enum value, a factory, a view component, and a
case in `DocumentView.tsx`.
:::

## Current limitations

Fifty-one types is a lot, and some of them are narrow. `POLICY_TESTIMONY`,
`LIFECOACH`, `LCEVENT`, and `SCRAPBOOK` each exist because one project needed
them. There is no mechanism for a type to be defined outside the enum, so every
new document type is a change to core files and a merge conflict waiting to
happen when two cohorts add types in the same term.

The prototype system has no migration story. If a prototype's field layout
changes after documents already exist, those documents keep the old shape.
