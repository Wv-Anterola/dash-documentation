## Why undo is a semantic layer

One user action can write many fields and documents: moving a group changes
several layouts; creating a link creates or resolves anchors and registers a
link document; an agent tool can tag a selection. Recording only the last field
assignment would restore an internally inconsistent state.

`UndoManager` therefore stores low-level `UndoEvent` records inside a higher-level
batch. `StartBatch` opens or nests a batch, `AddEvent` records mutations while
the manager is not itself replaying, and ending the outermost non-empty batch
pushes it to `undoStack`. Undo applies recorded setters in reverse order and
constructs the corresponding redo information; redo replays that inverse.

Decorators and wrappers provide entry points, but they cannot infer intent. The
feature author still decides whether several mutations are one action, whether
an asynchronous result belongs to the initiating action, and how failure cancels
or completes the batch.

## Undo batches

`UndoManager` groups mutations into a named conceptual action. Users expect one
undo to reverse what one visible action did.

Batch boundaries should wrap the mutation, not merely the UI callback that
started an asynchronous operation.

```text
begin named batch
  → validate inputs
  → mutate all affected documents
  → finish batch
```

For asynchronous work, avoid leaving the batch open across unrelated event-loop
activity. Use the async-aware wrapper intended for the operation.

## What belongs in one batch

One batch:

- Add a document and its initial layout
- Apply one agent tag action to several selected documents
- Create a link and both endpoint anchors
- Move a selected group as one gesture

Separate batches:

- A series of independently reviewable agent tool calls
- Several user actions inside a long-lived dialog
- External service calls whose results are accepted separately

## Agent write tools

Filter, sort, tag, and create-links actions are a persistent harm surface. Each
tool result should summarize the affected documents and the batch should be
individually reversible.

Undo is corrective control, not preventive permission. A tool can still expose
data to an external service or cause effects outside the Dash document graph.

## Action provenance

The experimental provenance layer associates:

- Tool name
- Validated arguments
- Timestamp
- Undo batch name
- Whether it is a write tool
- Source document/chunk that caused the action
- Success state and human-readable summary

Capture is globally gated and off by default in ordinary use. The research
prototype uses records as study stimuli and as a potential review affordance.

## Threat model

Indirect prompt injection arrives through content retrieved from a document.
If the model treats it as an instruction, it may select a write tool. Provenance
tries to make the causal source visible after the action.

It does not:

- Prove the model's internal reasoning
- Prevent the action
- Guarantee a reviewer notices the source
- Replace tool permissions or input validation

## Tests

- Multi-document action forms one batch.
- Consecutive agent tools form separate batches.
- Failed tool does not leave a corrupt partial batch.
- Undo restores ordering, visibility, tags, and links.
- Redo is deterministic.
- Provenance capture off is behaviorally inert.
- Capture on records source and summary without secrets.
- Imported adversarial text is represented as untrusted source content.
