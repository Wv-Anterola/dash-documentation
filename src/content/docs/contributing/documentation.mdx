This site is an [Astro](https://astro.build) project using
[Starlight](https://starlight.astro.build). Content is MDX in the repository;
there is no hosted editor and no account needed.

## Running it

```bash
git clone https://github.com/brown-dash/Dash-Documentation.git
cd Dash-Documentation
npm install
npm run dev
```

That serves the site at `http://localhost:4321/`.

The build targets a domain root by default. To build for a subpath instead, set
`DOCS_BASE` and `DOCS_SITE`:

```bash
DOCS_BASE=/Dash-Documentation DOCS_SITE=https://brown-dash.github.io npm run build
DOCS_BASE=/Dash-Documentation npm run links
```

Pages always link with site-root paths like `/concepts/documents/`. Starlight
rewrites the links it generates and `src/plugins/rehype-base-urls.mjs` rewrites
the ones you write by hand, so you never spell the prefix out yourself.

```bash
npm run build     # production build into dist/
npm run preview   # serve the built output
npm run check     # Astro + TypeScript diagnostics
npm run visuals   # rebuild lightweight posters from source screenshots/GIFs
npm run coverage  # capability, project, visual, and canonical-target coverage
npm run links     # internal link and anchor check over dist/
```

:::note[Why this is not Jekyll any more]
It was, until 2026. The problem was the toolchain: building the old site
required Ruby plus a C compiler, because `http_parser.rb`, `eventmachine`, and
`bigdecimal` all build native extensions. On a fresh Windows machine that meant
installing Ruby, gcc, msys2, and make before you could preview a typo fix.

Dash-Web is TypeScript on Node, so everyone working on Dash already has the
toolchain this site now needs.
:::

```text
      cohorts/

  data/
    capabilities.ts   canonical product inventory and source snapshot
    dash.ts           cohorts, concepts, statuses, people, helpers
    projects.ts       the forty-two project records
    visuals.ts        visual evidence for every project and capability
  styles/dash.css     palette and component styling
astro.config.mjs      sidebar and site configuration

```

Standard documentation behaviour comes from Starlight: sidebar, search,
breadcrumbs, table of contents, previous/next, mobile navigation, and dark
mode. Do not rebuild those.

## Adding a page

Create an `.mdx` file under the right directory in `src/content/docs/` with
frontmatter:

```mdx
---
title: Sentence case title
description: One sentence. This becomes the meta description and the search preview.
---
```

Both fields are required in practice. `description` is what a reader sees in
search results, and a page without one is much harder to find; every page on the
site has one, and it is worth keeping that true.

If the description contains a colon, quote it. Unquoted, YAML reads it as a
mapping and the build fails with "bad indentation of a mapping entry".

Then add it to the sidebar in `astro.config.mjs`.

The four groups under `Using Dash` are autogenerated from
`guides/features/`, `guides/documents/`, `guides/views/`, and
`guides/properties/`, so a new page in one of those directories appears without
a config change. Everywhere else is listed explicitly to control order.

A new *directory* under `guides/` does need a config edit, to give the group a
label. Autogenerating `guides` as a whole names each group after its directory,
which is how "tempMedia" ended up in the sidebar.

## Which section a page belongs in

The distinction that keeps the site coherent:

- **Concepts** explain an idea and why Dash represents it the way it does.
- **Capabilities** are the canonical statement of what Dash can do now.
- **Workflows** combine capabilities into an end-to-end task.
- **Detailed guides** explain individual controls and legacy interactions.
- **Architecture** and **Development** explain the implementation, for people
  changing it.
- **Research and history** records what a cohort did and what became of it.

A feature usually needs an entry in more than one. Its capability section is
canonical; concepts explain why, detailed guides explain controls, architecture
explains implementation, and research pages preserve provenance.

## Capability coverage

Add or update a record in `src/data/capabilities.ts` whenever integrated work
adds or materially changes product behavior. The record must include:

- User-facing title and summary
- Category and availability
- Real interface entry points
- Canonical user documentation target
- Canonical technical documentation target
- Verified source paths
- Every related project title

Every integrated project must appear in at least one capability record.
`npm run coverage` validates project names, mappings, and documentation
targets. Do not change a project to `integrated` until this check can pass with
truthful documentation.

The same check requires every project and capability to have a visual-evidence
entry in `src/data/visuals.ts`. A new feature is not fully documented when its
controls, state, or output can only be inferred from prose.

## Adding a cohort

Two edits, both in `src/data/dash.ts`.

**1. Add the cohort** to the `cohorts` array, newest first, and remove
`current: true` from the previous one. Exactly one cohort may be current;
`validate()` fails the build otherwise.

```ts
{
  id: '2027',
  title: 'Spring 2027 to Fall 2027',
  short: 'Spring/Fall 2027',
  current: true,
  start: '2027-01',
  end: '2027-12',
  commits: 0,
  summary: 'Two or three sentences on what the year was actually about.',
  roster: ['A Student', 'Another Student'],
}
```

You will also need to widen the `CohortId` union at the top of the file, which
is what makes a typo in a project's `cohort` field a type error.

For the commit count and roster, run this against a Dash-Web checkout:

```bash
git log --all --since=2027-01-01 --until=2027-12-31 --oneline | wc -l
git log --all --since=2027-01-01 --until=2027-12-31 --pretty=format:"%an" |
  sort | uniq -c | sort -rn
```

Use real names. If a GitHub account has no name attached and you cannot work
out whose it is, record the handle and say so, the way `Skitty1238` is handled
in the 2025 roster. Do not guess.

**2. Create the cohort page** at
`src/content/docs/research/cohorts/2027.mdx`. Copy an existing one; the file is
frontmatter, a few paragraphs about the year, and two components:

```mdx
<CohortRoster cohort="2027" />
<CohortProjects cohort="2027" />
```

Add it to the sidebar. Nothing else needs touching: the project index, the
cohort index, the people page, and the concept evidence tables all read from
the data.

## Adding a project

Add a record to `src/data/projects.ts`. Required fields are `title`, `cohort`,
`status`, `area`, `concepts`, and `problem`. Everything else renders only when
present, so a thin entry stays thin instead of producing empty headings.

```ts
{
  title: 'A short, specific name',
  cohort: '2027',
  status: 'integrated',
  area: 'Document model',
  concepts: ['documents'],
  people: ['Your Name'],
  problem: 'What was wrong or missing before, and why the absence mattered.',
  approach: 'The shape of the solution, and a choice someone else might not have made.',
  contribution: 'What you built. If half the work was making something not break, say so.',
  relation: 'How it connects to the rest of Dash.',
  outcome: 'Where it ended up, including what does not work.',
  evidence: 'What you checked to justify the status.',
  tech: ['TypeScript', 'React'],
  code: '`DocumentType.YOURS`; branch `your-branch`',
}
```

`area` and `concepts` are what stop a project from being stranded on one page.

`area` groups the project in the index and in its summary tables. Reuse an
existing value where one fits.

`concepts` puts the project into the evidence table on each concept page you
list, and puts a link back to those concepts in the project write-up. This is
the mechanism that keeps documentation and project record pointing at each
other, so it is worth a minute rather than left empty.

Add the project’s visual to `projectVisuals` in `src/data/visuals.ts` in the
same change. Prefer an exact current capture or the original archived demo. If
neither exists, use the closest honest feature-family image, set its scope to
`Representative Dash interface`, and include a project-specific `brief` that
states exactly what the replacement capture must show. Never label a family
image as the project itself.

## Citing a project from a documentation page

When a feature exists because of a specific project, say so where the feature
is documented:

```mdx
import ProjectNote from '../../../components/ProjectNote.astro';

<ProjectNote title="Graph view for collections">
  Why this project matters to the page you are on right now.
</ProjectNote>
```

The component looks the project up in `src/data/dash.ts` and renders its
cohort, contributors, and status, so that metadata cannot drift out of sync.

Write the note fresh for each place you use it. Do not paste the project's own
summary in: the reader can follow the link for that, and what they need here is
the sentence explaining why it matters on this page.

A mistyped title throws at build time. That is deliberate. The previous Liquid
version rendered an HTML comment and the reference silently disappeared.

## Choosing a status honestly

This is the part that makes the rest of the site worth trusting. The
[status taxonomy](/reference/status-taxonomy/) sets out what evidence
`integrated` requires. If your branch is not merged, the status is
`implemented`, and that is a normal outcome rather than a failure.

## Writing conventions

Sentence case for headings and navigation, and no trailing colon on a heading.
A heading should say what the section covers: "What you can do" rather than
"Objects & Actions".

Reference assets from `/assets/...`, which resolves against the configured base.

Write alt text on every content image. Most images here are screen recordings,
and an empty `alt` makes them invisible to anyone who cannot see them. Describe
what happens in the recording, not what the file is called.

The one exception is an icon sitting in a table beside its own name, as in the
sidebar and top bar tables on
[the Dash workspace](/getting-started/environment/). Those keep `alt=""` on
purpose: a screen reader already reads the label in the next cell, and
describing the icon as well just says everything twice.

Do not link the words "here", "this page", or "learn more". Name the
destination, so the link still means something read out of context: "see how the
graph view connects to the layout engine" rather than "read more".

If a feature is removed from Dash, do not delete its page. Add a `:::danger`
aside explaining when it went, and set the project status to `archived`. The
[physics simulations page](/guides/documents/simulations/) is the worked
example.

If a page is a stub, say so in a `:::caution` aside and name what would close
it, the way [scripting](/guides/features/scripting/) and
[layout](/guides/properties/layout/) do. Two sentences dressed up as a page is
worse than two sentences admitting it.

## Visual capture standard

Use a real screenshot or short recording when the interface, spatial
relationship, or state change is materially easier to understand visually.
Do not add decorative screenshots that repeat the preceding sentence.

Every final capability image should:

- Use the current documented Dash-Web revision.
- Contain synthetic or explicitly approved content.
- Hide usernames, local paths, tokens, private URLs, and browser extensions.
- Show enough interface chrome to locate the action.
- Crop empty desktop/browser space.
- Use a 16:9 or 4:3 master at least 1600 pixels wide.
- Export as WebP for stills unless transparency requires PNG.
- Use restrained callouts that remain readable in dark and light themes.
- Have alt text describing the information conveyed, not visual decoration.

For motion, keep the recording under 20 seconds when possible, begin in a
stable state, pause on the result, avoid rapid cursor movement, and ensure the
same procedure is available in prose.

Every project and canonical capability must have visual evidence in
`src/data/visuals.ts`. The registry distinguishes current product captures,
exact archived demos, archived feature recordings, and representative
interfaces. This provenance label is part of the evidence and must stay
visible.

Animated recordings can be very large. Add the original path as `source`, add
its lightweight poster name to `scripts/build-visual-posters.mjs`, and run
`npm run visuals`. Pages display the poster and link it to the full recording,
which keeps the index fast without hiding the interaction.

When a final page-level capture is not available, use
`MediaPlaceholder.astro`. A valid placeholder names the intended filename and
ratio, specifies the exact scene to capture, and supplies final-quality alt
text. Replace the component with the real asset; do not turn the placeholder
canvas into an image.

## Before you commit

```bash
npm run coverage && npm run check && npm run build && npm run links
```

`coverage` validates project/capability mappings and canonical targets. `check`
runs Astro and TypeScript diagnostics, which is what catches a mistyped project
title before the build does.

The link checker walks the built output and reports broken internal links,
broken anchors, missing images, images with no `alt` attribute, and headings
that skip a level.

It has one blind spot worth knowing: it treats `alt=""` as present, so an image
written `![](/assets/...)` passes. Emptiness is a legitimate choice for a
labelled icon and a bug everywhere else, and no checker can tell which you
meant. Search for `![](` before you commit.
